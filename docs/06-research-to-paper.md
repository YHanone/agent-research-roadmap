# 从问题到投稿

## 第一步：选择具体方向

方向必须收敛成“任务场景 + 失败现象 + 可测指标”，例如：

> 在仓库级修复任务中，Coding Agent 经常在连续测试失败后重复相似修改。能否依据失败类型决定继续局部修复还是重新规划，从而在固定调用预算下提高成功率？

“研究 Agent Memory”不是题目；“构建更强 Coding Agent”也不是可验证问题。

## 第二步：建立技术认知

- 精读 5-8 篇核心论文，结构阅读 10 篇左右相关工作。
- 建立表格：问题、机制、任务、模型、预算、指标、主要结果、限制。
- 找出大家共同采用但未充分验证的假设。

## 第三步：复现一个适中基线

本科生首个复现应满足：

- 有官方代码和自动评测。
- 可在 20 个样本上完成 pilot。
- 不要求训练 7B+ 模型。
- 能替换或关闭关键模块。
- 失败轨迹可以保存和人工检查。

首选 SWE-agent/Agentless 的小子集或自建可公开的小型 repository task；不要先跑完整 SWE-bench。

## 第四步：从失败中找问题

将失败按原因拆分：定位、规划、编辑、工具、测试理解、上下文、停止决策、环境。统计频率，并检查分类一致性。

优先选择同时满足以下条件的问题：

- 至少占失败的一定比例，不是极少数个例。
- 可以通过日志或自动指标识别。
- 在两个模型或两个任务子集上出现。
- 解决它不需要训练大模型。
- 有清晰的反例和失败判据。

## 第五步：提出研究假设

好的假设必须允许失败：

```text
观察：连续两次同类测试失败后，Agent 常重复局部编辑。
原因假设：Agent 没有根据反馈判断当前计划是否已失效。
预测：引入可解释的重规划触发器后，重复编辑率下降；
      在相同调用预算下，特定失败子类的解决率提高。
反证：重复编辑下降但成功率不变，或收益只来自额外调用。
```

## 第六步：设计实验

最小实验矩阵：

- 原始方法。
- 强简单 baseline。
- 你的完整方法。
- 移除核心组件的版本。
- 相同额外调用次数的重采样 baseline。

至少报告：任务成功率、成本/token、步骤数、运行时间、错误恢复率和失败类型。指标选择必须对应 hypothesis。

## 第七步：消融与对比

消融不是随意关模块，而是回答机制问题：

- 触发器是否必要？
- 反馈内容还是额外计算带来收益？
- 阈值变化是否稳定？
- 对哪类任务有效，对哪类无效？
- 换一个模型或任务子集后是否仍成立？

## 第八步：整理结果和写作

先写三句话：

1. 现有方法在什么条件下有什么问题。
2. 提出什么机制，为什么可能解决。
3. 哪些实验支持或限制这个结论。

然后先冻结表格和图，再写方法与实验，最后写引言和摘要。标题和摘要不能超过实验支持范围。

## 第九步：选择投稿场所

按贡献类型选择，而非只看名次：

- 新的学习/推理方法：ICLR、ICML、NeurIPS 等，门槛很高。
- NLP Agent 与评估：ACL、EMNLP、NAACL 及 Findings。
- Software Engineering Agent：ICSE、FSE、ASE、ISSTA 等。
- 早期但完整的结果：相关 workshop。
- 系统性长期实验或扩展研究：再考虑匹配 scope 的期刊。

正式投稿前查看当届 call for papers、匿名和生成式 AI 政策。不要用往年政策代替当届要求。

## 有价值且低成本的创新类型

- **诊断型贡献**：发现并验证一个被总平均掩盖的系统失败模式。
- **评测型贡献**：构造能区分现有方法的新扰动、指标或任务子集。
- **效率型贡献**：在相同成功率下降低调用、token 或延迟，或在固定预算下提高成功率。
- **机制型贡献**：证明某模块为何有效、何时无效，并给出更简单方案。
- **数据型贡献**：经过严格构建和验证的失败轨迹或小型 benchmark。

不应包装为创新：只换 Prompt、只换模型、只调温度、只加一个现成模块、只在极小样本上提高几个点。
