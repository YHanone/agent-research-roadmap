# 论文阅读与复现方法

## 一、先判断是否值得读

用 10-15 分钟完成第一轮筛选：

1. **问题是否与你的方向相关？** 不因标题含 Agent 就阅读。
2. **贡献是否可验证？** 是否有明确任务、baseline、指标和代码。
3. **证据是否覆盖 claim？** “通用”“自主”“长期”等词是否真的被实验支持。
4. **对照是否公平？** 模型、调用次数、token、工具和测试预算是否一致。
5. **是否有后续影响？** 看被哪些工作采用或质疑，但不把引用量当质量本身。

分为三类：

- **精读**：与你当前问题直接相关，或是必须复现的基线。
- **结构阅读**：只需要掌握问题、方法和实验结论。
- **检索使用**：只查某个定义、数据集或实现细节。

## 二、三遍阅读法

### 第一遍：20-30 分钟，建立地图

- 读摘要、引言、所有图表、结论和 limitations。
- 写下：问题、方法、主要 claim、最强证据。
- 不在公式和实现细节上停留。

### 第二遍：1-2 小时，重建方法

- 画出输入、状态、模型调用、工具、记忆、输出和评测的数据流。
- 对每个模块追问：删掉会怎样？它解决了什么失败？
- 明确训练时与推理时的区别。
- 列出不可见变量：Prompt、模型版本、最大步数、温度、重试策略。

### 第三遍：带着复现目标阅读

- 对照代码定位入口、配置、数据和评测脚本。
- 建立“论文描述 → 配置项 → 代码位置 → 输出指标”的映射。
- 只深挖复现核心 claim 必需的部分。

## 三、理解实验设计

阅读实验时填写下面的因果结构：

```text
研究假设 H：
改变的变量 X：
保持不变的变量：
观察指标 Y：
主要 baseline：
潜在混淆因素：
如果 H 错误，预期观察：
```

Agent 论文尤其检查：

- 是否给不同方法相同模型和调用预算。
- 是否把重试、搜索或并行采样的成本算进去。
- 任务是否可能出现在模型训练数据中。
- 环境和外部 API 是否随时间变化。
- LLM-as-a-judge 是否经过人工抽查。
- 只报告平均值是否掩盖了高失败率子类。

## 四、寻找可改进问题

不要从“我能加什么模块”开始，从失败和假设开始：

1. 复现作者最重要的结果。
2. 收集失败轨迹，不急于修改方法。
3. 建立失败分类，并让第二个人抽查一部分标注。
4. 找到高频、可测量且跨任务出现的失败。
5. 写出原因假设和一个最便宜的证伪实验。
6. 只有原因得到初步支持后才设计方法。

值得研究的信号：

- 方法在某类任务上系统失效，而非几个特例。
- 提升依赖更高预算，公平预算下消失。
- 某模块在论文中没有消融或替代基线。
- 环境扰动、工具报错或模型变化导致结论不稳定。
- 最终成功率相同，但过程成本和风险差别很大。

## 五、GitHub 复现流程

### 1. 复现前冻结信息

- 论文版本、commit SHA、依赖版本。
- 数据集版本、模型/API 精确名称。
- Prompt、temperature、seed、最大步骤和预算。
- 评测脚本版本。

### 2. 分三级运行

- **Smoke test**：1-3 个样本，验证流程和日志。
- **Pilot**：10-20 个样本，估算成本并发现配置问题。
- **Full run**：只有 pilot 稳定后才扩大。

### 3. 先复现原方法，再修改

不要一边修代码一边加入自己的方法。原始复现与改进实验使用独立配置和输出目录。

### 4. 处理结果不一致

按顺序检查：

1. 评测脚本和数据版本。
2. 模型/API 版本和 Prompt。
3. 最大步骤、重试和 token 限制。
4. 依赖、环境和工具返回值。
5. 随机波动与样本选择。

结果不一致本身不是创新。只有证明偏差稳定、原因明确并具有一般意义，才可能形成研究贡献。

## 六、复现完成标准

- 一条命令可运行最小实验。
- 配置与代码分离。
- 每条轨迹带唯一 ID、时间、预算和结果。
- 原始输出不可手工修改，表格由脚本生成。
- README 说明硬件、成本、已知偏差和失败样本。
- 至少复现一个主要结果和一个关键消融。
